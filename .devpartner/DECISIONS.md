| ADR-001 | 2026-10-05 | Consume published flood science rather than implement a hydrodynamic solver                  | Staff Software Architect + Data Engineer        | A: Build a 2D shallow-water solver in-app. B: Consume pre-computed flood extents/depths from published research and visualize them. C: Call a hosted commercial flood API per scenario.                                                             | **Chose B.** McClean, Walsh, Lwasa & Ddumba (2021, Newcastle + Makerere) published modelled Kampala flood extents from a 2D finite-volume hydrodynamic model on a 5m DEM, sampling 20/40/60/80/100mm rainfall over 1/3/6-hour durations at 0.1/0.2/0.3m depth thresholds (DOI 10.5285/e53dea2e-cb25-4f0f-b5f9-937eecf15aff). The hydrology is peer-reviewed, locally-authored, and openly licensed. Building a solver duplicates work already done by Uganda's own university at lower fidelity and forfeits the credibility that "computed by Makerere researchers" carries. C adds a paid dependency and a latency path inside an interactive 3D loop, and commercial flood APIs do not cover Kampala.                                                                                                                                                                                                              |
| ADR-002 | 2026-10-05 | Run the 3D view as a progressive enhancement over a 2D fallback, not as the primary UI       | Product Owner + Accessibility Advocate          | A: 3D canvas is the product; 2D is an appendix. B: 2D depth grid is guaranteed to work; 3D is an enhancement layered on top with equivalent data access.                                                                                            | **Chose B.** Target users are on mid-range Android over mobile data, and a WebGL2 scene at city scale is a real risk to LCP and to users on older GPUs. The flood risk numbers must remain reachable without WebGL — this is also the WCAG 2.2 AA path, since a canvas is not accessible alone.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| ADR-003 | 2026-10-05 | Represent flood depth as discrete threshold classes, never as continuous point values        | Staff Data Engineer + Product Owner             | A: Render continuous per-cell water depth (implied by the published depth thresholds). B: Render one polygon set per depth threshold and expose depth only as a class — ">=0.1m", ">=0.2m", ">=0.3m".                                               | **Chose B.** Verified against the publisher's own catalog record (ERR-001): the dataset is a GeoPackage of _vector extents_, and the thresholds were applied before publication. There is no per-cell depth value in the source. Displaying continuous or interpolated depth would fabricate precision we do not have — for an insurer or a planner that is a correctness failure, not a cosmetic one. Three stacked extent classes give a legible, honest readout matching what the study actually supports.                                                                                                                                                                                                                                                                                                                                                                                                         |
| ADR-004 | 2026-10-05 | Terrain from Copernicus DEM GLO-30 (30m), not the study's 5m DEM                             | Staff Software Architect                        | A: Obtain the Makerere 5m DEM. B: Copernicus DEM GLO-30 — 30m, free & open, public S3 bucket with STAC. C: Fetch terrain tiles from a commercial provider at runtime.                                                                               | **Chose B.** The 5m DEM is a research _input_ to McClean et al., not a published output, and is not distributable (ERR-002). GLO-30 needs no registration, serves Cloud Optimized GeoTIFF with HTTP range support — letting us request only the byte ranges covering Kampala instead of a global tile — and Uganda is not in the restricted tile set. C breaks the zero-credentials rule and adds per-load cost. The 30m-vs-5m gap is real and is disclosed in every output rather than hidden (RISK-007).                                                                                                                                                                                                                                                                                                                                                                                                            |
| ADR-005 | 2026-10-05 | 3D geometry is built in metres, Y-up, origin at the study-area centroid — never in NDC       | Staff Software Architect + Data Engineer        | A: Normalized device coordinates (-1..1), reusing the existing `lonLatToNdc` helper. B: Metres, Y-up, origin at the extent centroid. C: Metres, Y-up, origin at the south-west corner.                                                              | **Chose B.** Kampala has ~1,000m of relief across ~20km, so vertical exaggeration is mandatory for the hills to be visible at all. That exaggeration must be a single disclosed number, statable in the UI and in the generated risk report (RISK-007) — in NDC it becomes entangled with the projection and is no longer a physically meaningful ratio. Metres also keeps `computeVertexNormals` correct, keeps camera near/far planes physically sane, and gives OSM footprints and flood polygons one shared space to snap to terrain. The 2D fallback is a map, not a camera view, and deliberately does _not_ share coordinates with the 3D scene. A was rejected despite `lonLatToNdc` already existing — its presence is not a reason. C wastes float32 precision and pushes the camera 20km from the origin.                                                                                                  |
| ADR-006 | 2026-10-05 | Terrain grids must have a uniform _cell size_, not a square cell count                       | Staff Software Architect + QA Engineer          | A: Require `rows === cols`. B: Require `width/(cols-1) ≈ depth/(rows-1)` within 0.5% relative drift.                                                                                                                                                | **Chose B.** The study extent is not square (WGS84: ~19,258m E-W × ~22,336m N-S — see ADR-007), so a 30m grid is 643 × 746. Option A rejects the exact grid GLO-30 will produce and would force either padding the extent (dead columns, distorted footprint) or two different cell sizes (a terrain stretched north-south, corrupting every measurement taken off it). Uniform cell size is also the invariant that catches the real corruption mode: a DEM binary whose header disagrees with its payload. Tolerance is relative so it scales with grid size; 0.5% absorbs the ≤0.23% drift that `round(extent / cell) + 1` produces across the three quality tiers. Originally recorded in PROJECT_STATE as "throw on non-square grids" and corrected during Unit 1b.                                                                                                                                              |
| ADR-012 | 2026-10-06 | Intercept network in tests with MSW, pinned to the v2 line                                   | Test Strategist + Library Evaluation Specialist | A: `msw@2.15.0` pinned. B: `msw@3.0.2` (current latest). C: stub `fetch` with `vi.fn()`.                                                                                                                                                            | **Chose A.** The first network call is the first chance for test doubles to drift from what a browser actually does — MSW intercepts at the network layer, so status codes, `response.ok`, and `arrayBuffer()` are exercised for real. C is disqualified by the project's own mocking discipline (never stub `fetch` directly) and would have hidden exactly the transport branches being tested. B crashed on first use inside `@mswjs/interceptors` → Node 24's bundled undici (`RequestInit: Expected signal ... to be an instance of AbortSignal`, ERR-008) with no application code involved; swapping to A passed all seven tests unchanged, which is what localised the fault to the dependency rather than the tests. Dev-only, MIT (verified from its manifest), and the pin is deliberate: upgrading msw is a decision to re-run the transport suite against the new interceptor stack, not a routine bump. |
| ADR-011 | 2026-10-06 | pnpm's own manifest sets the Node floor; build-script allowlists live in pnpm-workspace.yaml | DevOps / Platform Engineer                      | A: Keep `engines: ^20.19.0` and the `pnpm` field in `package.json`. B: Take the floor from pnpm 11's manifest (`>=22.13`), CI matrix `['22.13.0', '24']`, and `allowBuilds: { esbuild: true }` in `pnpm-workspace.yaml`. C: Drop pnpm for npm/yarn. | **Chose B.** pnpm 11.16.0 bundles `node:sqlite` and declares `engines: node >=22.13`, so it cannot run under Node 20 at all — option A's engine-floor job would have failed forever, and my earlier ERR-005 correction had enshrined an unreachable floor. pnpm 11 also warns and ignores the `pnpm` field in `package.json`; the allowlist key is `allowBuilds` in `pnpm-workspace.yaml`. With A, a cold-store install exits 1 with `ERR_PNPM_IGNORED_BUILDS` while a warm local store hides it — a gate green locally and red in CI is the failure mode ADR-009 exists to prevent. The allowlist is minimal (esbuild only) rather than `dangerouslyAllowAllBuilds`: allowing build scripts is a claim about which dependencies execute code, and claims should be enumerated. C rejected: pnpm is already invested in and the lockfile exists.                                                                      |

| ADR-010 | 2026-10-05 | Resampling to the terrain grid is a tested pure module; `geotiff` decodes the COG but never resamples it | Data Engineer + Staff Software Architect | A: Hand-roll TIFF IFD, Deflate and FP-predictor decode plus the resample in one script. B: `geotiff` for I/O and decompression, custom resample in a unit-tested module, script for orchestration. C: Let `geotiff` read and resample in one call, no custom maths. | **Chose B.** The tile is Deflate-compressed with a floating-point predictor, so A is not a reasonable option. C is the smallest code and it was tempting, but it would make the resample untestable — and a transposed or flipped resample produces a plausible terrain with no error anywhere. B keeps `readRasters` on `nearest` so the source samples are exact and all interpolation happens in `demResample.ts` under 26 tests, including ramp and anisotropy cases a flat field cannot catch. Independently cross-checked: `geotiff`'s own bilinear resample of the same window agrees at **Pearson 0.997**, mean | diff | 1.67m over 479,678 samples, the residual explained by my grid anchoring to the exact WGS84 bounds while geotiff's anchors to the window pixel grid. The geometry module takes the study extent as an argument rather than importing `geo.ts`, so `scripts/fetch-dem.mjs` stays the single composition point and the module keeps no hidden coupling to one city. |
| ADR-009 | 2026-10-05 | CI mirrors the local commit gate exactly, and asserts the test-collection scope | DevOps / Platform Engineer | A: Minimal pipeline (install + test). B: Full commit-gate mirror plus an engine-floor matrix and a test-scope assertion. C: Delegate to a hosted CI service. | **Chose B.** A pipeline that runs different checks from the local gate drifts from it, and then it either passes something the developer would have rejected or blocks something they just fixed. Order is format → lint → type-check → test → build. Two additions are earned by specific failures rather than caution. The **engine-floor matrix** turns `engines.node` from a comment into a verified claim — the declared range was `>=20.0.0` while Vite 7 requires `^20.19.0`, so Node 20.0–20.18 satisfied our declaration and could not build (ERR-005). The **test-scope assertion** guards ERR-003, where 145 dependency suites inflated a 61-test suite to 1,498 and still reported green. C was rejected as inappropriate for a repo this size and as a paid dependency the core product does not need. |
| ADR-008 | 2026-10-05 | Cache the DEM as a custom uint16 binary with a self-validating header | Staff Software Architect + Performance Engineer | A: Ship float32 samples (1.83MB). B: Custom uint16 binary with a 48-byte header storing dims, metre extent, and the observed min/max band. C: Ship the source COG tile (~36MB) or a PNG of elevations. | **Chose B.** First load must fit ≤3MB compressed _and_ also carry flood extents (RISK-008). uint16 halves the terrain to **0.92MB**, and it is not a real precision compromise: the step is `range / 65535`, so on a 200m band it is ~3mm — two orders of magnitude below the 30m source resolution. Quantisation can therefore never be the reason a visual artefact appears, which is what lets us disclose 30m-vs-5m honestly (RISK-007). The header is stored little-endian via explicit `DataView` reads with no host-endianness assumption, and the declared byte length is checked against the actual buffer length so truncation throws instead of yielding a short terrain. The band is stored **per file** rather than fixed, so the step adapts to the relief actually present; `MAX_DEM_QUANTISATION_STEP_METERS = 0.01` marks the width at which uint16 would stop being transparent and would require uint32. A was rejected as affordable but wasteful; C is disqualified by the payload budget outright. |
| ADR-007 | 2026-10-05 | Reproject WGS84 with the ellipsoid, not a mean-radius sphere | Staff Software Architect + Data Engineer | A: Keep `EARTH_RADIUS_M = 6_371_008.8` and multiply every degree span by it. B: Full WGS84 — meridian m/deg from M(φ) = a(1−e²)/(1−e²sin²φ)^1.5, parallel m/deg from N(φ)cos(φ) = a·cos(φ)/√(1−e²sin²φ). C: An equirectangular projection about the extent's mid-latitude, applied in one place. | **Chose B.** Option A is what `geo.ts` already did, and it was wrong by **125m north-south** and **−21m east-west** over Kampala's extent — opposite signs, so the axes drifted apart by ~146m over 22km (ERR-004). It passed the existing tests because those only asserted loose order-of-magnitude bounds. A sphere is a fair approximation at continental scale and a bad one at city scale, and this tool reports distances and exposed population to planners. C was rejected because it hides the same approximation behind a transform name; the per-axis scale factors need to be independently testable, and now they are. Bounds tests are tightened to ~500m ranges plus exact-value regression pins so the sphere cannot silently return. |
