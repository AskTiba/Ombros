## Architecture Decisions

| ID      | Date       | Decision                                                                               | Persona                                  | Options considered                                                                                                                                                                                    | Chosen rationale                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| ------- | ---------- | -------------------------------------------------------------------------------------- | ---------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ADR-001 | 2026-10-05 | Consume published flood science rather than implement a hydrodynamic solver            | Staff Software Architect + Data Engineer | A: Build a 2D shallow-water solver in-app. B: Consume pre-computed flood extents/depths from published research and visualize them. C: Call a hosted commercial flood API per scenario.               | **Chose B.** McClean, Walsh, Lwasa & Ddumba (2021, Newcastle + Makerere) published modelled Kampala flood extents from a 2D finite-volume hydrodynamic model on a 5m DEM, sampling 20/40/60/80/100mm rainfall over 1/3/6-hour durations at 0.1/0.2/0.3m depth thresholds (DOI 10.5285/e53dea2e-cb25-4f0f-b5f9-937eecf15aff). The hydrology is peer-reviewed, locally-authored, and openly licensed. Building a solver duplicates work already done by Uganda's own university at lower fidelity and forfeits the credibility that "computed by Makerere researchers" carries. C adds a paid dependency and a latency path inside an interactive 3D loop, and commercial flood APIs do not cover Kampala. |
| ADR-002 | 2026-10-05 | Run the 3D view as a progressive enhancement over a 2D fallback, not as the primary UI | Product Owner + Accessibility Advocate   | A: 3D canvas is the product; 2D is an appendix. B: 2D depth grid is guaranteed to work; 3D is an enhancement layered on top with equivalent data access.                                              | **Chose B.** Target users are on mid-range Android over mobile data, and a WebGL2 scene at city scale is a real risk to LCP and to users on older GPUs. The flood risk numbers must remain reachable without WebGL — this is also the WCAG 2.2 AA path, since a canvas is not accessible alone.                                                                                                                                                                                                                                                                                                                                                                                                          |
| ADR-003 | 2026-10-05 | Represent flood depth as discrete threshold classes, never as continuous point values  | Staff Data Engineer + Product Owner      | A: Render continuous per-cell water depth (implied by the published depth thresholds). B: Render one polygon set per depth threshold and expose depth only as a class — ">=0.1m", ">=0.2m", ">=0.3m". | **Chose B.** Verified against the publisher's own catalog record (ERR-001): the dataset is a GeoPackage of _vector extents_, and the thresholds were applied before publication. There is no per-cell depth value in the source. Displaying continuous or interpolated depth would fabricate precision we do not have — for an insurer or a planner that is a correctness failure, not a cosmetic one. Three stacked extent classes give a legible, honest readout matching what the study actually supports.                                                                                                                                                                                            |
| ADR-004 | 2026-10-05 | Terrain from Copernicus DEM GLO-30 (30m), not the study's 5m DEM                       | Staff Software Architect                 | A: Obtain the Makerere 5m DEM. B: Copernicus DEM GLO-30 — 30m, free & open, public S3 bucket with STAC. C: Fetch terrain tiles from a commercial provider at runtime.                                 | **Chose B.** The 5m DEM is a research _input_ to McClean et al., not a published output, and is not distributable (ERR-002). GLO-30 needs no registration, serves Cloud Optimized GeoTIFF with HTTP range support — letting us request only the byte ranges covering Kampala instead of a global tile — and Uganda is not in the restricted tile set. C breaks the zero-credentials rule and adds per-load cost. The 30m-vs-5m gap is real and is disclosed in every output rather than hidden (RISK-007).                                                                                                                                                                                               |

## Technology / Dependency Choices

| ID       | Date       | Library/Tool              | Version   | Why chosen                                                                                                                                                                                                                                                             | Rejected alternatives                                                                                                                                                                                               |
| -------- | ---------- | ------------------------- | --------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| TECH-001 | 2026-10-05 | @react-three/fiber + drei | current   | Declarative scene graph maps to React's data flow; the flood surface's rendered state is a direct function of a `depthGrid` prop, which is exactly the reactive model R3F gives. Drei supplies camera controls, LOD, and helpers that would otherwise be hand-written. | Raw Three.js imperative code (loses the reactive binding that makes scenario changes a prop update rather than a manual scene rebuild); CesiumJS (heavy, geared to globe-scale, and unnecessary for a single city). |
| TECH-002 | 2026-10-05 | PostgreSQL + Drizzle ORM  | 16 / 0.4x | Scenario definitions, saved reports, and audit trail are relational and query-heavy. Drizzle keeps the SQL visible for the spatial aggregates risk scoring needs, and matches the stack convention established across this portfolio.                                  | SQLite/Postgres.js — spatial queries and concurrent report generation make SQLite a poor fit; Prisma — heavier runtime and weaker support for the raw spatial SQL we need.                                          |
| TECH-003 | 2026-10-05 | Zod                       | 4         | Validates scenario definitions at the API boundary. Scenario params (rainfall depth, duration, intervention geometry) are user-supplied and drive the render loop — unvalidated they are a correctness and injection surface.                                          | Valibot (faster, but less ecosystem traction in the existing stack); hand-rolled guards (unmaintainable at boundaries).                                                                                             |
